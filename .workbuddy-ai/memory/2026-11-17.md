### 发现并修复的 bug（全部未提交，留在工作区）

1. **HIGH · warm start 会永久丢失 WAL-only 的新会话**：`loadDump()` 把 `sqliteIngestAt` 重置为当前时间（30s cooldown），`main()` 又在 `dumpRestored > 0` 时整批跳过 deferred heavy refresh，而 `watch.ts` 的 startup scan 在 `!primed && canSkipStartupIngest()` 时直接 return、不排队重试。若引擎停机期间只往 `state.vscdb-wal` 写过一次且之后不再变化，这次变更永不解析，且每次重启 cooldown 重置 → 永久丢失。
   - 修复：`SessionStore.sqliteWalReparseDelayMs()` 暴露剩余 cooldown；`watch.ts` 在 startup skip 和 `ingestIfSession` 跳过解析后，用 `scheduleIngest(path, delay+250)` 排一次延迟复查；`scheduleIngest` 增加可选 `delayMs`。精确匹配不会排复查。
2. **MEDIUM · `openStream` 重复重连 / 泄漏 EventSource**：`onerror` 闭包引用可变的 `es` 而非自身 socket，且 `retryTimer` 无去重。同一 socket 多次 CLOSED error 会排多个 timer → 多个活跃 SSE；旧 socket 迟到的 error 会关掉新 socket；`stop()` 只关最后一个。
   - 修复：connect 内捕获局部 `source`，`es === source` 守卫、`retryTimer` 单次守卫、connect 开头清 timer；新增 3 个回归测试。
3. **MEDIUM（潜在）· `store.refresh()` 把未解析的 WAL 指纹写进 nextFingerprints**：deferral 分支原本 `set(resolved, current)`，等于声称已解析那份 WAL。改为保留 `recorded`（当前生产路径只传 lightFiles，属潜在问题）。
4. **LOW · `sessionsError` 轮询堆叠请求**：`refreshList(true)` 绕过 `listInFlight` 去重，`listSessions` 超时 45s，卡住的引擎会叠 ~15 个请求。加 `retryInFlight` 守卫，每次轮询等上一次 settle。
